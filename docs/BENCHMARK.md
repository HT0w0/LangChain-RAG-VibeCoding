## 1. 分词器冷启动
jieba 的主词典是**进程级**的,但每个新建的 `Tokenizer` 实例第一次
分词时都要把它读进内存。与语料大小无关,是一次固定成本。

| 场景 | 中位数 | p95 |
|---|---|---|
| 新建 Tokenizer 后第一次分词 | 249.8 ms | 259.1 ms |
| 同一实例第二次分词 | 20.8 µs | 23.1 µs |
| 复用分词器后每次分词 | 17.3 µs | 21.2 µs |

**读法**:第一行与第二行的差就是词典加载成本,约 **249.8 ms**。
第三行是分词器复用之后每次分词的实付代价。旧实现每个请求新建一个
`Tokenizer`,于是每个问题都为同一本从不变化的词典重付一次这一项。

## 2. BM25 关键词路
一次完整的 `_search_bm25`:分词器 + 全量建索引 + 检索 top20。
「冷启动」列每次都清掉分词器缓存(等价于旧实现的每次新建)。

| 语料规模 | 冷启动 | 分词器已热 | 差(冷 − 热) | 占比 |
|---|---|---|---|---|
| 200 分块 | 266.9 ms | 29.0 ms | 237.9 ms | 89% |
| 1000 分块 | 396.2 ms | 148.7 ms | 247.4 ms | 62% |
| 3000 分块 | 665.7 ms | 414.4 ms | 251.3 ms | 38% |

**读法**:「差」列是两次测量的差值,**不是直测的词典加载**——纯词典加载
的权威数字在第 1 节。差值在大语料上会**高估**它:两次测量的差别不止词典
一项,还含建索引时的内存分配与 GC,而这一项随语料变重。所以 3000 分块
那一格比另两格高,是差值法放大了噪声,不是词典变大了。

真正要看的是一件事:这一项**不随语料规模增长**。200 → 3000 分块,建索引
从几十毫秒涨到几百毫秒(十余倍),而词典加载始终在同一个量级。它是**固定
成本**。缓存粒度因此取在分词器上:按索引缓存会在每次语料写入后失效、把
固定成本重新付一遍;按分词器缓存则跨越语料变更持续有效。

## 3. 缓存读写
`CacheStore` 的每次读写都自开会话并提交,量到的是一次真实往返。

**量的是自持会话那种模式**(`CacheStore(db)`)。另一种
`CacheStore.on(session)`,把写入并进调用方已有的事务,省掉开会话与
提交——它存在的理由是别的:摄取时调用方持着 SQLite 写锁,另开会话
会死锁(`database is locked`)。那条路径不在这里测,因为它的耗时
取决于调用方的事务,**不是一个可以单独量出来的常数**。

| 载荷 | 大小 | 写入 | 命中 | 未命中 |
|---|---|---|---|---|
| 向量(1024 维 float32) | 4096 B | 1.1 ms | 710.3 µs | 780.1 µs |
| 检索(20 个 chunk id) | 240 B | 1.1 ms | 720.9 µs | 727.7 µs |
| 答案(约 4KB) | 4096 B | 1.1 ms | 695.9 µs | 684.2 µs |

**读法**:三档载荷的耗时几乎一样(240 B 与 4096 B 的差别看不出来),
说明这一层的代价**不随条目大小变化**,而是每次操作固定的一次开销:
开一个会话、走一次提交。命中(710.3 µs)与未命中(727.7 µs)
几乎相同——「真的取回一行」本身几乎不花钱,开销全在开会话与提交上。
**注意命中并不比未命中快**,差的符号在两次运行之间会翻,因为它俩的差别
已经落进噪声里了。

这条结论有两个直接后果。一是**别指望靠压缩条目大小提速**——要省就得省
操作次数,`CacheStore.get_many` 的批量读就是为此存在的(入库时几百个分块
逐个查会把「批量」的意义抵消掉)。二是这层的成本下限由 SQLite 往返决定,
与它挡住的那次网络编码或 LLM 往返差着两三个数量级——这是三层缓存值得
存在的前提;哪天换成更廉价的本地模型,这个前提需要重新测。

## 这些数字支持了什么

基准本身不产生价值,它只是让三个已经做出的决定变得可核对:

1. **缓存粒度取在分词器而不是索引上。** 词典加载是一次固定成本,按索引缓存
   会在每次语料写入后失效、把固定成本重新付一遍;按分词器缓存则跨越语料变更
   持续有效。第 1、2 节的差值就是这个选择的收益,而且是**可复现的**。

2. **BM25 索引仍然整份重建。** 第 2 节的「复用分词器」列里,建索引的开销随
   语料线性增长,这部分没有被缓存掉,也不该被缓存掉——增量维护 BM25 的 IDF
   要重算全局文档频次,换来的复杂度远大于它省下的时间,还会引入「删了文档
   索引里还在」这类难查的漂移。

3. **缓存值得落 SQLite。** 第 3 节说明一次往返在毫秒级,而它挡住的是网络
   编码与 LLM 生成。这个量级差是三层缓存能成立的全部依据;若哪天上层引入
   了更廉价的本地模型,这个结论需要重新测。
