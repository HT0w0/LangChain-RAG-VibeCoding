# 并发压力测试

**测的是「很多人一起用」,不是「单次请求多快」** —— 后者在 `BENCHMARK.md`。

- 时间:2026-10-10 18:58:17
- 机器:Windows 11 / Python 3.13.14 / 16 逻辑核
- profile:**mock**
- 重复:阶梯每档观测**两次**(升序一遍、降序一遍),不是三次。
  这是**对消顺序**的做法而不是取中位数:单调上探时 WAL 在增长、
  CPU 在热降频、缓存在冷热之间漂移,这些自变量与「负载」混在一起;
  反过来再跑一遍能把「顺序」这个因素对消掉。**两个方向给出的膝盖不一致时,
  报告两个,不挑一个。**

> ⚠️ **压测生成器与被测服务跑在同一台机器上**,两者抢同一批核。
> 多数偏差(CPU 争抢、热降频)会把服务器测得**更差** —— 那是保守的。
> 但**客户端**连接池没放开会让实际并发低于目标,把服务器测得**更好**,
> 所以每张表都报**实测的 in-flight 并发峰值**,而不是「我打算压多少」。
> (注意分清楚:**服务端**自己也有一个连接池,那个是本轮真正打到的那一个 ——
>  见第三节的根因。)

## 二、阶梯:系统能撑到哪一档

**主判据是失败率,不是延迟的某个倍数。** 这一条是改过的:原先只按「p95 涨到最低档的 3 倍」判,而最低档的 p95 只有几毫秒 ——「3 倍」于是只有十几毫秒,**在 6ms 和 23ms 之间画条线,对「能撑多少人」毫无意义**。判据没算错,但它回答的是个没人关心的问题。

所以:**失败率是主判据**(无歧义,不需要挑倍数),延迟曲线是被解释的对象(用首 token 时延 —— 总时长被模型的大常数延迟盖住,会把本地排队的信号稀释掉)。

## 三、服务端出过什么异常

**这一轮客户端一个请求都没失败。** 下面列的是**服务端日志里出现过的异常** —— 它们**没有变成用户看得见的失败**,而且绝大多数是客户端主动断连留下的取消异常(压测里很常见:一条流挂到时间上限就被掐掉)。

所以「第二节说每档都是 0 失败、第三节却列出若干异常」**并不矛盾**:前者是**用户看到的结果**,后者是**服务端记下的事件**。

**那为什么还要列?** 因为「没失败」和「没出过事」不是一回事。这些异常现在无害,但**数量突然变大就是个信号** —— 它是这条链路最灵敏的一根温度计。

**服务端日志里出现过的异常**(按出现次数排):

- `37 次  asyncio.exceptions.CancelledError: Cancelled via cancel scope <id> by <Task pending name='sse_starlette.sse.EventSourceResponse.__call__.<locals>.cancel_on_finish' coro=<TaskHandle._run_coro() running`
- `1 次  ConnectionResetError: [WinError 10054] 远程主机强迫关闭了一个现有的连接。`

## 四、登录风暴:argon2 会不会堵住事件循环
**主判据是事件循环探针**:挂着 4 个客户端反复打 `/api/health`,量**两次响应之间的间隔**。

为什么不用 SSE 流当判据(实测踩到过):一次问答的答案会进**答案缓存**,而缓存的答案是「整段一次发出」的 —— 第二遍问同一句话时**根本没有 token 流可看**。冒烟跑出来的症状是基线臂收到 114 个间隙、后面三臂各只有 12 个:不是没停顿,是**没东西可量**。探针不做问答,对缓存免疫,而它测的是**同一个因** —— 循环被占住时,一个已经在等的请求会跟着等。

**判据赛前定死**:风暴臂的探针间隔 p99 ≥ 基线的 5 倍,且 ≥ 20ms(后者用来跨过 Windows ~15.6ms 的计时器量化地板)。

| 臂 | 探针 p50 | 探针 p99 | 相对基线 p99 | 循环可用性(次/秒) | 相对基线可用性 | 流间隙 n |
|---|---|---|---|---|---|---|
| 空载基线 | 3.1 ms | 4.7 ms | 1.0× | 1368 | 100% | 1584 |
| 30 并发廉价请求 | 4.1 ms | 10.9 ms | 2.3× | 1016 | 74% | 1876 |
| CPU 饱和 | 3.4 ms | 5.0 ms | 1.1× | 1272 | 93% | 1468 |
| 30 并发登录 | 4.2 ms | 14.6 ms | 3.1× | 924 | 68% | 1685 |
**读法**:判别因果的**不是**登录臂自己涨没涨,而是**四条臂的对比**。

  * **「循环可用性」那一列比 p99 更好读** —— 它直接回答「事件循环还有多少空档留给别人」:100% 表示没受影响,掉到 60% 表示有四成时间被占住了。
  * 「CPU 饱和」臂也涨 → 停顿是 **CPU 被抢**,不是事件循环被占。
    这两种原因症状很像,却指向完全不同的修法。
  * 「廉价请求」臂也涨 → 是**请求数本身**造成的,与 argon2 无关。
  * 只有「登录」臂涨 → 才归因到 argon2 占住了事件循环。

⚠️ **「CPU 饱和」臂是粗对照,不是配对对照。** 它制造的是「机器上有别的重负载」,消耗的 CPU 总量也与 30 次 argon2 不相等。**真正配对的是「修与不修」的 A/B**(同样的 argon2 工作,只挪出事件循环),归因以那一组为准。

## 五、客户端与服务端对账

**只对账「问答」请求。** `request_metrics` 是问答链路独有的(在 `chat.py` 里写),浏览类请求不落那张表 —— 把浏览也算进来会凭空造出一个「差额」,然后被误读成「指标写入被吞了」。

| | 值 |
|---|---|
| 客户端发出的问答请求 | 6139 |
| 服务端记录到的 | 6124 |
| 差额(服务端 − 客户端) | -15 |

⚠️ 服务端**少记了 15 条**。这个差额里混着两种**完全不同**的东西,要分开说,不能笼统当成「网络丢包」:

  1. **客户端根本没发出去的**(连接层失败:ReadError / ConnectError):本轮 0 条。这些请求压根没到服务端,不记是**对的**。
  2. **发出去了、服务端却没记上的**:剩下的 15 条。**这一部分才是问题。**

  第 2 类为什么危险:指标写入失败在本项目里是**被吞掉的**(`metrics.py:114-121`)—— 而在连接池打满的情况下,**写指标那一次也需要一条连接,它同样拿不到**。于是:请求因为拿不到连接而失败 → 记这次失败又要一条连接 → 也失败 → 被吞。症状是**错误率被低估,而且最慢的那批请求从分布里消失,p95 反而更好看**。

  ⚠️ 本轮**无法把第 2 类精确归因** —— 要坐实得在服务端数「进到路由的请求数」,而现在的指标表本身就不完整。这条记为待查。

## 六、这份测试**没有**覆盖的

- **不改服务端指标结构**(用户已定):所以服务端那一栏区分不出超时 / 429 / 客户端断连,分类在客户端侧做。
- **不做分布式压测**:只有一台机器,生成器与服务同机争抢,所以绝对延迟是**上界偏保守**,而实际并发峰值需要逐表核对。
- **不测文档摄取**:解析走 `BackgroundTasks`,与请求在同一个事件循环里却**没有包线程池** —— 那是另一条独立的问题线,本脚本不覆盖。
- **不测真实平台的并发上限**:mock profile 假设外部服务可无限扩展,**若真瓶颈在供应商,它会高估可达容量**。real profile 只做小剂量校准。
- **测不到内存峰值。** 本环境里读别的进程的常驻内存是坏的(实测:裸解释器、导入 fastapi+chromadb、只导 json 三个对照进程读到的都是同一个 4.6MB),所以 S4 那几臂跑的时候会打印「RSS=测不到」,而不是一个数字(那一行只在终端上,不进这张表)。
  这一条对本轮结论有实际影响:argon2 是**内存硬化**算法(每次哈希 64MB),把它挪进线程池的代价正是内存压力,而**那个代价本轮没有实测数据** —— 只知道代码里给它加了并发闸门(预算 512MB ÷ 64MB = 8 个并发)。

### 本次运行的备注

- 本轮测在**连接池扩容之后**：pool_size 从默认 5 提到 20、max_overflow 从 10 提到 100（合计容量 15 → 120），pool_timeout 从默认 30 秒降到 10 秒。
- 修之前的同一套阶梯：并发 20 档失败 0–30/200、并发 50 档失败 176–188/200，全部是 HTTP 500。根因是 sqlalchemy.exc.TimeoutError: QueuePool limit of size 5 overflow 10 reached, connection timed out, timeout 30.00 —— 服务端 572 次池超时与客户端 572 次 500 精确对上，一比一。
- 改动最直接的效果：并发 50 档从 176–188/200 失败变成 0/200，并发 100 档也不再崩。
- ⚠️ 扩池是**抬天花板，不是治本**。真正的毛病是「一次请求从头到尾握着连接」，修法应该是检索完就还、流式期间不持有。这一点写在 app/db/base.py 的注释里。
