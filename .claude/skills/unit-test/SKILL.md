# unit-test：写单元测试 · 跑 · 出报告

这个项目**已经有 615 条后端 + 62 条前端测试，且绝大多数是测试先行写出来的**。
所以第一件事不是「写测试」，是**判断哪里真的还没有**——

> 「为这个项目的代码生成单元测试」的真实含义是**找出没有覆盖的地方**，
> 不是把已有的行为再断言一遍。重复的测试不会多抓到一个 bug，只会多一份
> 要跟着改的东西。

判断依据是**读代码 + 读现有测试**，不是看有没有同名文件：
`app/services/parsing.py` 没有 `test_parsing.py`，但它其实被 `test_kb.py`
通过上传接口覆盖了一部分——按文件名判断会得出完全错误的结论。

## 第一步：先判断这块代码该不该有单元测试

| 要测的东西 | 结论 |
|---|---|
| `app/services/`、`app/indexing/`、`app/core/`、`app/providers/` 里的解析与纯逻辑 | ✅ 写 |
| 后端接口的**行为**（权限、状态码、落库结果）| ✅ 写 —— 走 `TestClient`，这是项目的既有惯例 |
| `frontend/src/api/` 里的纯函数（`sse` / `citations` / `errors`）与取值逻辑 | ✅ 写 |
| `frontend/src/components/*.tsx`、`frontend/src/pages/*.tsx` | ❌ **不逐个写** —— 由 `App.test.tsx` 的整树挂载 + 逐页渲染覆盖。组件样式错了肉眼一看就知道，而整树挂载已经能抓到「页面打不开」这类致命问题 |
| `app/schemas/` 里的声明式模型、`frontend/src/api/types.ts` | ❌ 不写 —— 运行时没有东西可测。**例外**：有行为的字段（如 UTC 序列化）已经在 `test_schemas.py` 里，那里有一条守卫用例专门盯「有没有漏挂」 |
| 需要联网 / 真实 API 的东西（embedding、rerank、LLM 的真实行为）| ❌ 不写 —— 归 `backend/scripts/` 下的探针脚本。单元测试必须能离线重复跑 |

**碰到 ❌ 那几行：停下告诉用户「这块按项目现有做法不写单元测试，理由是……」，再问他要不要换个做法。不要硬做。**

## 🔴 不许动地基

写测试时，下面四件事**一件都不许做**：

- 装新依赖（`pytest-cov`、`coverage`、`jsdom`、`@testing-library/*`……）
- 改 `pyproject.toml` / `conftest.py` / `vite.config.ts` / `package.json`
- 改被测源码，好让测试写得出来
- 自己新搭一套测试胶水层

**这不是「实现细节」，是改技术选型。** 那四个文件里每一个决定都有代价，
而且代价写在项目的 README 与代码注释里。

| 为自己找的理由 | 实情 |
|---|---|
| 「不装 coverage 就不知道盖了多少」 | 想知道的其实是「哪里没测」。读代码能回答这个；覆盖率百分比不能——它能告诉你某行执行过，但告诉不了你**断言有没有意义** |
| 「反正只 `--no-save` / 只装在临时目录」 | 一样是把选型改了。代价是「别人克隆下来跑不起来」 |
| 「我抄一份工具内部的胶水就行」 | 那是在项目里埋一份会和上游悄悄脱节的副本 |
| 「我把源码改成可测的形状就行」 | 改了源码，测试绿了，而业务逻辑被动了、用户不知道。见下面「测试没过」 |

**需要动地基时：停下，把「为什么需要、要装什么、代价是什么」讲给用户，等他说了再动。**

## 第二步：写

**放哪。** 后端放 `backend/tests/test_<模块>.py`；前端与被测文件**同目录同名** + `.test.ts`（`sse.ts` → `sse.test.ts`）。

**照抄同目录已有测试的风格。** 这两个项目各有一套：

```python
# 后端
async def test_中文描述_这条钉住了什么行为(self) -> None:
    """为什么这条用例存在——**以及它防的是哪种静默失效**。"""
```

```ts
// 前端
it('中文描述', () => { ... })
```

**注释写「为什么这条测试存在」，不复述代码。** 这个项目里注释的分量很重，
因为它们记的是踩过的坑——照那个标准写。

**测行为，不测实现。** 断言「给什么输入出什么输出」，别断言「内部调了几次」。
优先走**公开入口**：测 `parse_document(path, filename=...)` 而不是 `_parse_html(path)`。
项目里确实有几处直接测私有函数（`_usage_from`、`_raise_for_upstream`），
但那是例外，且都带了 `# noqa: PLC2701` 说明是刻意的。

**造夹具不许引入新依赖。** 要一个 `.docx`,就用已经装了的 `python-docx`
现造一个；要 `.xlsx` 就用 `openpyxl`。这些都是被测代码自己的依赖，不算新装。

## 第三步：跑

```bash
# 在仓库根目录跑。`.venv` 里那个 python 才是装了 pytest / ruff 的
.venv/Scripts/python.exe -m pytest -q                    # 后端全量
.venv/Scripts/python.exe -m pytest backend/tests/test_parsing.py -q   # 只跑你新写的
.venv/Scripts/python.exe -m ruff check backend/app backend/tests backend/scripts

cd frontend && npm run test                # 前端全量
npx tsc -b                                 # 测试文件也在类型检查范围内
```

**跑全量，不只是你新写的那几个文件。** 新用例通过、而某条旧用例红了，
那也是这次改动造成的——必须一并报告。

## 第四步：报告（照这个形状，别超）

```
**结果**：通过 X 项 / 共 Y 项（新增 N 项）      ← 一行，放最前

**新增了什么**：<每个新测试文件一行：测什么、钉住哪条行为>

**没通过的话**：<原样贴报错，不转述；说清是「测试写错了」还是「源码有 bug」>
```

全过且无失败时，**报告不超过 10 行**。

不要写进报告：勘察过程、跑过哪些命令、对被测代码的长篇评价。

## 测试没过

**只报告，不改源码。** 先分清是哪种，并**给出证据**：

- **测试写错了**（断言写错、夹具构造错、路径不对）→ 说清并改测试
- **源码有 bug** → 说清，**停下等用户发话**。别顺手改源码 —— 测试绿了，但业务逻辑被动了、而用户不知道

这个项目里真实撞到过的「看起来像源码坏了、其实是测试写错了」：

- 夹具里写死了 `user_id=1` / `session_id=1`，但临时库里没有这两行，
  而 `PRAGMA foreign_keys=ON` 让插入被拒；更隐蔽的是写指标的那一层
  **按设计吞掉异常**，症状只是「表里一行都没有」，看不出和外键有任何关系
- 测试多套了一层 `service.stream(...)`，把 `PreparedAnswer` 换成了异步生成器，
  报的是 `AttributeError`——而同一个文件里另外 20 个调用点传的都是对的

**先问「这个失败是不是我造夹具的方式造成的」，再问「是不是源码坏了」。**

## 反向辨识（按需，不是每次都做）

新增的检查要证明它**真的会红**。项目里已用的做法是：
临时把实现改坏（删掉一个分支、把 `>=` 改成 `>`、把路由名改掉）→
确认**恰好对应用例失败** → **立刻还原**。

- **值得做**：防**静默失效**的用例（越界编号不当作引用、闭区间边界、
  `0` 与 `None` 的区分、脚本/样式标签要被剥掉）
- **可以省**：明显在测一个纯计算的
- **不许用脚本批量改写源码再跑**：那会动到生产代码而你事后很难确认还原干净。
  用编辑器改一处、跑、改回来
- 报告里**只写一行**结果，别展开

做完确认 `git status` 只剩你新加的文件。
