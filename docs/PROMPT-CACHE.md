# prompt 缓存:平台一直在给这个读数,我们一直在把它丢掉

> 数据来源:`backend/scripts/prompt_cache_probe.py`,实测于 2026-10-09,
> `qwen3.7-plus`(百炼 OpenAI 兼容端点)。
> **本文的数字与平台当下的行为绑定**——缓存策略不写在任何合约里,
> 换模型或平台调整策略都必须重跑探针。

## 这件事的起因

`Usage` 里原本只有三个字段:`prompt_tokens`、`completion_tokens`、`total_tokens`。
而百炼的回包里其实还有一个:

```json
"prompt_tokens_details": {"cached_tokens": 1664, "text_tokens": 1751, ...}
```

**它被整个丢掉了**——Provider 没解析它,SSE 的 `done` 里没有它,指标表里没有
这一列。于是「这一轮的 prompt 有多少是缓存供给的」这个问题,在日志、接口、
面板上**都无从回答**,只能靠猜。

这一层是**隐式**前缀缓存:没有 API 要调,没有开关要开,命中与否只体现在这个
读数上。所以「看不见它」和「它不存在」在系统里的表现是一样的——
而这正是花一个下午把探针跑出来的理由。

## 为什么它会命中

前缀缓存命中的是**已经见过的、一模一样的前缀**,省掉的是那段前缀的重新编码。
在一条 RAG 链路上,唯一稳定的前缀只有 system 提示:

```
[system: 只依据资料作答 + 标注 [N] + 资料是数据 ]   ← 每轮一字不改
[user:   【资料】<每次检索都不一样> + 【问题】<每次不一样> ]
```

实测这个 system 提示是 **244 token**(365 字符)。而 `smoke_e2e.py` 在真实链路
上量到的整份 prompt 是 **286 token**——也就是说 **system 占了 85%**,
剩下那 15% 才是【资料】和【问题】。

这个比例让缓存这件事比看上去重要得多:如果那 244 个能稳定命中,单轮请求的
输入开销就能省掉八成以上。所以「它到底命中没有」是个值得花时间量的问题,
而不是一个可看可不看的读数。

> 顺带一提,`services/prompts.py` 早就为此做了设计——**资料放 user、不放
> system**,理由写在那个模块的文档里。下面第四行会说明:这个设计是**必要
> 的**,但在实测里**不充分**。

## 测量方法

四个形状各发一次,全部用 uuid 拼进提示词,保证**每次运行都是全新的前缀**:

| # | 形状 | 对应生产里的什么 |
|---|---|---|
| ① | 冷启动(全新前缀) | 第一次部署 |
| ② | 原样重复 | 同一个问题被问两遍 |
| ③ | 只换问题(**尾部分歧**) | 同一份资料、换个问法 |
| ④ | 只换资料(**前部分歧**) | **每次提问都会重新检索——线上每轮都是这个形状** |
| ⑥⑦ | 多轮(历史原样保留并追加) | 同一会话的相邻两轮 |

**缓存是账号级的**,同一份文本之前跑过就直接命中——所以「冷启动」这一格必须
用唯一前缀起步,否则量出来的是上一轮的残留,整个实验的前提就没了。

## 实测结果

两次独立运行逐格一致:

| 情形 | cache_read | 占比 |
|---|---|---|
| ① 冷启动(全新前缀) | **0** | 0% |
| ② 原样重复 | 2304 | 83% |
| ③ 只换问题(尾部分歧) | 2304 | 83% |
| ④ **只换资料(前部分歧)** | **0** | **0%** |
| ⑤ 回到 ② 那条 | 2304 | 83% |
| ⑥ 多轮:首轮 | 2304 | 57% |
| ⑦ 多轮:再来一轮 | 2304 | 57% |

### ③ 与 ④ 是一对,它们才是结论

- **③ 只动尾部 → 83% 照样命中。** 前缀匹配是真的:把问题从「多少钱」换成
  「库存多少」,前面那段共用资料仍然被复用。
- **④ 只动前部 → 0%。** system 一字未改,但仍然**一个 token 都没命中**。

第二行是这次测量里最要紧的一格。它推翻了一个很自然的假设——「命中的是从头
到第一个分歧点的那段前缀」。按那个假设,④ 至少该命中 system 那 244 个;
实测是 0。

**意味着:`prompts.py` 里「资料放 user 以保住 system 前缀」这个设计是必要的,
但不充分。** 每次提问都会重新检索,所以线上每一轮长得都像 ④。
在这个形状下,当前测不到任何缓存收益。

### 多轮那一行

⑥⑦ 是唯一一个能稳定看到非零的场景——同一会话的相邻两轮之间,前缀
`[system, 上一问, 上一答]` 完全一致。但即使把历史加进去,命中的绝对量仍是
2304,没有随前缀变长而增长。

### 真实链路上量到的是 0

上面那张表用的是**人造的长 prompt**(2780 token),而真实链路短得多。
`smoke_e2e.py` 里那一轮问「RX9070 显卡多少钱」的实际回包:

```
"usage": {"prompt_tokens": 286, "completion_tokens": 20, "total_tokens": 306,
          "cached_tokens": 0, ...}
```

**286 个 prompt token,一个都没命中。** 紧接着的追问(带 2 条历史,前缀与上一轮
开头完全一致)同样是 `cached_tokens: 0`——与上面说的「新写入的条目有可见性
延迟」吻合:两轮之间隔不到一秒。

真实的语料比探针小一个量级(只有两份商品资料),所以这里更接近冷启动的
形状。结论不变,而且更直接:**当前配置下,真实流量里的 prompt 缓存收益
观测不到。**

## 这个测量证明不了什么

- **没能解释机制。** 为什么④是 0 而③是 83%,我试过三种解释(块对齐、
  最长公共前缀、整段精确匹配),**没有一种能同时对上全部七行**。
  这个脚本给的是**可复现的观测**,不是一份机制说明。
- **读数不稳定。** 同一个前缀在不同时刻命中的长度会不同——新写入的条目有
  可见性延迟。这一点在早期的手工实验里撞到过两次:完全相同的 prompt 紧接着
  重发,一次读到 0、一次读到 2304。所以**多跑几次比只看一次可靠**。
- **换模型就作废。** 探测用的是 `qwen3.7-plus`;别的模型可能压根没有这一层,
  或者换一套对齐规则。

**所以结论不是「缓存怎么工作」,而是「这一层不能靠推理,只能靠观测」。**
这也正是下面这件事的意义。

## 接进指标(这一步真正的交付)

读数现在一路走到面板:

```
Provider 回包 → Usage.cached_tokens → SSE 的 done.usage.cached_tokens
              → request_metrics.cached_prompt_tokens
              → 面板的 cached_prompt_tokens / cache_read_rate
```

两个刻意的决定:

| 决定 | 理由 |
|---|---|
| **`None` 表示「平台没报」,`0` 表示「平台说没命中」** | 含义相反。合并之后面板上会是一条平稳的 0% 命中率曲线,看起来像「缓存一直不工作」,而事实是我们根本没在听。与 `first_token_ms` 用 `None` 表示「一个字都没流出来」是同一条理由 |
| **命中率的分母只算报过读数的请求** | 把没报读数的算进分母,命中率会被系统性拉低——而拉低的方向恰好是「缓存看起来更没用」,与真实情况相反 |

「没调模型的一轮」(命中答案缓存、或检索为空走固定答复)属于**没报读数**,
记 `None` 而不是 `0`:`prompt_tokens` 补 0 是对的(那是「这一轮花了多少」的
如实回答),而缓存读数是「平台说了什么」——没问过平台,就没有读数。

于是「缓存到底有没有在工作」这件事不再需要跑探针脚本才知道:**真实流量里
的命中率就在面板上**,而这个数来自真实问法,比上面那张手写语料扫出来的表
可信得多。

## 重跑方式

```bash
python backend/scripts/prompt_cache_probe.py
```

**联网、花钱、依赖平台当下的行为。** 它的价值在于能重跑,不在于某一次的结论。
换 LLM 模型之后必须重跑:`cached_tokens` 的尺度与命中规则都随模型而变。
