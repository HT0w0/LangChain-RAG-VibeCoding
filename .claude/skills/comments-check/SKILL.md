# comments-check：注释检查

## 两条路，缺一不可

| | 查什么 | 地位 |
|---|---|---|
| **主检查** | 注释的内容和代码**对不对得上** | 这才是重点 |
| 副检查 | 注释数量够不够 | 只是个**报警器** |

**必须先做完主检查再说数量。只报比例 = 没检查。**

一条**错**的注释比没有注释更害人 —— 它会让人照着一个错的说法去改代码。

## 一、怎么数（跑脚本，不许自己心算）

```bash
node .claude/skills/comments-check/count-comments.mjs .
```

口径已经写死在脚本里，**只管调用，不许自己数**：

- 分母 = 非空行
- 分子 = **独占一行**的注释（行尾的行内注释不算）
- TS/TSX：`//` 整行、`/* */` 整块（续行每行都算）
- **Python：`#` 整行 + docstring 的正文行**

⚠️ **「docstring 算注释」这一条是本项目特有的，而且是必须的。** 实测（2026-10-09）：
`backend/app` 只数 `#` 是 **12.7%**，把 docstring 算上才是 **33.6%**。这个项目的
「为什么」几乎全写在 docstring 里（`store_upload` 为什么用 uuid、`security.py`
为什么 JWT 不放 role，都是）。只数 `#` 的话，工具会对着一个注释写得比谁都认真的
目录报「需要补注释」。

**脚本自己也有自检**（12 项，`--selftest`）。它出错的后果是静默的 —— 报出一个
漂亮的百分比而它是错的。迁移当天就撞到过一次：捕获组读错一位，整个 Python
目录被算成 100% 注释，脚本一声不吭。**改了这个脚本一定要跑一遍自检。**

## 二、三档标准

| 板块 | 要求 | 实测（2026-10-09） |
|---|---|---|
| 后端 `backend/app/` | ≥ 30% | 33.6% |
| 前端 `frontend/src/` | ≥ 15% | 17.5% |
| 整体（产品代码） | ≥ 25% | 29.6% |

阈值是**实测值向下取整到 5 的倍数**，不是拍脑袋定的。留余量是为了让它平时是绿的
—— **一道总在响的警报等于没有警报**。

`backend/scripts/`（探针与演示，联网才跑得起来）和测试文件**只报数、不设要求**：
它们回答的是另一个问题。测试文件的注释要说的是「这条用例防的是哪种静默失效」。

## 三、绝不做的事：凑数的废话注释

**比例是报警器，不是目标。**

看到某个文件只有 3%，**不要说「这里需要补注释」** —— 那会逼出这种东西：

```python
# 定义变量
total = sum(items)
# 返回结果
return total
```

三条害处：读的人白花时间；它跟着代码一起过期、变成假话；真正需要的注释反而被淹没。

**判断一条注释该不该存在，只问一句：删掉它，读代码的人会失去什么？**

- 失去「**为什么**这样做」→ 该留
- 什么都没失去（代码本身就一目了然）→ 废话，**不要建议加**

本项目现有注释就是这个水平：写**决策和代价**。`parsing.py` 讲为什么表格类和
叙述类要分开对待；`cache.py` 讲为什么嵌入缓存**不**带 generation 而另外三层都带。
**你建议补的注释必须达到这个水平 —— 达不到就别建议。**

## 四、主检查怎么做

对每个有注释的函数/代码块，读注释、读代码，判三种情况：

| 情况 | 怎么认 |
|---|---|
| ✅ **对得上** | 注释说「k=60 出自 Cormack SIGIR 2009」，代码里就是 `RRF_K = 60` |
| ❌ **对不上**（最严重） | 注释说「存储层是 naive UTC」，代码却在往外写带时区的值 |
| ⚠️ **过期** | 描述的行为改过了，注释没跟上 |

顺带留意这三类瑕疵：**重复注释**（两段挂在同一个东西上）、**自相矛盾**、
**引用了已消失的东西**（不存在的文件、改了名的函数、被否决的方案）。

**这几类地方最容易注释失真，重点扫：**

- 有历史包袱的代码（踩过坑、改过好几版）—— `rag.py`、`cache.py`、`schemas/common.py`
- 边界处理（空值、除零、分位数定义、`0` 与 `None` 的区别）
- 和外部约定绑死的代码（百炼端点形状、SSE 事件协议、SQLite 的时间语义）
- **文档里的数字**：README 与 `docs/` 里有大量实测值（延迟、阈值、包大小）。
  代码改了之后它们极易过期，而过期的数字**看起来仍然像事实**。

## 五、报告形状（读的人不懂编程）

```
**结论**：注释和代码对不对得上 —— 一句话。          ← 最前面

**对不上的地方**：                                 ← 主检查，放前面
  - <文件:行> —— 注释说什么、代码实际做什么、为什么这有害

**数量**：整体 X%（要求 25%）｜后端 app A%（要求 30%）｜前端 src B%（要求 15%）

**建议**：<只列真的值得改的，按严重程度排>
```

**规矩：**

- **只报告，不改代码。** 用户说补才补。
- 全过时**不超过 10 行**。
- **不要**贴：跑了哪些命令、完整的比例表格、对每个文件的逐条评价。
- 数量那一段，**只在真的偏低时提**；不要罗列所有文件。
