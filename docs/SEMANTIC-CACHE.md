# 语义缓存:阈值是怎么定下来的,以及为什么它默认关闭

> 数据来源:`backend/scripts/semantic_probe.py`,实测于 2026-10-09,
> `qwen3.7-text-embedding`(1024 维)。
> **本文的数字与模型版本绑定**——换 embedding 模型必须重跑探针,余弦的
> 绝对尺度随模型而变,旧阈值不作数。

## 这一层在做什么

三层缓存里,前两层的键是**精确匹配**:键不一样就一定不命中,错了也只是
没命中,代价是「这次慢一点」。

语义缓存不是。它按问题向量的**最近邻**取答案——「RX9070 显卡质保多久」
和「RX9070 显卡保修几年」问的是同一件事,应当复用同一份答案,而它们的
问题文本哈希完全不同,精确键永远匹配不上。

换来的是这一层独有的一种失败:

> **把另一个问题的答案发出去。**

而且那份答案是**完整的**:措辞通顺、来源编号对得上、`grounded` 为真、
来源卡片能展开。所有表面信号都正常。它只是回答错了。

再加上一点:命中率的提升和错配率完全在同一个旋钮上(阈值),调低阈值
同时抬高两者——**指标面板上看不出错配**,它只会显示缓存工作得很好。

所以这一层的阈值必须测出来,不能拍一个。风险还是**单侧**的:

| | 后果 |
|---|---|
| 假阳性(错配) | 用户拿到另一个问题的答案,不知道为什么错 |
| 假阴性(漏检) | 一次未命中,走正常链路,用户感知不到 |

错配要防,漏检可以忍。这就是阈值取在实测区间**上方**的全部理由。

## 测量方法

构造两类问题对,用真实 embedding 编码后算余弦:

- **应命中**(8 对):同一意图的不同问法,答案相同。
  例:「支持七天无理由退货吗」↔「七天无理由退货能不能办」
- **不应命中**(12 对):同一个商品,但问的是**另一个属性**,答案完全不同。
  例:「K870 机械键盘保修多久」↔「K870 机械键盘多少钱」

关键在构造方式:每一对只在「问的是哪个属性」或「换成了哪种说法」上不同,
而不是随便挑两句长短不同的话——后者算出来的分数说明不了任何事。

判据是**阈值扫描**,不是两个极值相减。早期版本拿「应命中的最低分」减
「不应命中的最高分」,只要有一个离群点就得出「不存在安全阈值」的结论,
而那个结论对调参毫无用处。正确问法是:对每个候选阈值,数出多少漏检、
多少错配。

重跑:

```bash
python backend/scripts/semantic_probe.py
```

## 实测结果

分布:

| | n | min | median | max |
|---|---|---|---|---|
| 应命中 | 8 | 0.7658 | 0.9569 | 0.9896 |
| 不应命中 | 12 | 0.4812 | 0.6982 | **0.7924** |

两类的中位数差了 0.26,确实是两个分布。但**下界有重叠**——这就是阈值
必须扫描、不能取中点的原因。

阈值扫描:

| 阈值 | 命中 | 错配 | |
|---|---|---|---|
| 0.60 | 8/8 | 9/12 | |
| 0.65 | 8/8 | 8/12 | |
| 0.70 | 8/8 | 4/12 | |
| 0.75 | 8/8 | 1/12 | |
| 0.78 | 7/8 | 1/12 | |
| **0.80** | 7/8 | **0/12** | ← 零错配起点 |
| 0.82 | 7/8 | 0/12 | |
| **0.85** | 6/8 | 0/12 | ← 零错配区间上界 |
| 0.88 | 6/8 | 0/12 | |
| 0.90 | 5/8 | 0/12 | |
| **0.95** | 5/8 | 0/12 | ← **当前配置** |

**零错配区间:`(0.7924, 0.8491]`,宽度 0.0567。**

读法:

- **下界 0.7924 由最危险的那条错配决定**,而它不是「不同商品」那一类
  (那类分数反而低),而是:

  ```
  0.7924  K870 机械键盘保修多久  ‖  K870 机械键盘多少钱
  ```

  同一个商品,只差一个属性词。这提示了一件事:这一层**真正难的地方不是
  认出「在说同一个商品」,而是分得清「在问这个商品的哪一件事」**。
- **区间内取舍为零**:0.80 到 0.85 之间任意阈值都是错配 0、命中 7/8。
- **高出 0.8491 就开始拿命中率换安全**,而这是唯一安全的方向。

## 当前取值与它的代价

配置里是 **0.95**(见 `Settings.SEMANTIC_CACHE_THRESHOLD`),在零错配区间
上方约 0.16。

这不是区间内命中率最高的选择——0.80 能多拿 2/8 的命中。**多出来的那两个
命中,买的是「这批样本之外的问法也会在区间里」这个假设**,而这个假设
本探针证明不了(见下节)。在错配与漏检代价不对称的前提下,为安全多付
一点命中率是划算的。

代价要讲清楚:**在这个 8 对的近义改写样本上,0.95 只命中 5 对(62.5%)。**
也就是说即使打开这一层,也只有约六成的换一种问法能被复用,另外四成
照常走完整链路。这不是一个「开了就很快」的开关。

## 这个测量证明不了什么

必须说清楚,否则上面的数字会被当成保证:

1. **样本是自己写的问题对,24 条,一个领域。** 它证明了「零错配区间存在」,
   没有证明「真实用户的问法都落在区间里」。用户会写出探针作者想不到的
   句式,尤其短问句和错别字密集的——而短问句的向量更容易和无关键词的
   另一句话撞上。
2. **单侧覆盖。** 12 条错配全部是「同商品不同属性」和「同属性不同商品」。
   「不同商品不同属性」这一类明显更容易分开,没有构造,因为构造了也
   不构成风险。
3. **一次快照。** 服务端的 embedding 模型可能被更新,而更新不会通知。
   0.7924 这个数换个月跑可能就变了。

**所以这一层的默认状态是关闭**(`SEMANTIC_CACHE_ENABLED=False`),而不是
「开着一个保守的阈值」。关闭时唯一的损失是命中率,那是一个可以接受的
默认;开着而错配,是用户拿到错误答案且无人察觉。要用它就得显式打开,
并接受上面那三条。

## 接进链路时要注意的

**它必须排在向量缓存之后启用。** 查一次语义缓存需要一次问题向量;没有
向量缓存时,每次未命中都要白搭一次网络编码(实测约 157 ms),把最常见
的路径拖慢——而缓存该做的是让常见路径更快。所以 `get_rag_service` 里
同一个 `CachedEmbedder` 实例同时交给检索链和这一层。

**位置在 `prepare()` 里、精确答案缓存之后、改写之前。** 排在精确缓存之后
是因为那一层只要一次按哈希的读,比一次向量比较还便宜;排在改写之前是
安全的,而且不是巧合——这一层只在没有历史时生效,而没有历史时
`rewrite_question` 走早退分支原样返回问题,两个位置对它可能命中的每一次
请求都等价。

**带历史的提问一律不走这一层**,读和写两侧都挡。在答案缓存上这是个谨慎
的选择,在这里是必须的:「它多少钱?」在两个会话里的向量**完全相同**,
比措辞不同还更容易跨会话命中。

**失效靠语料代次,不靠 TTL。** scope 里带当前语料代次,任何写入使代次 +1,
旧条目立刻读不到。文档被删掉之后,缓存里那条答案的来源编号会指向一个
不存在的片段——而它照常显示成一张可展开的来源卡片。TTL 只负责回收空间。

**命中时以 `answer_cache_hit=True` 上报**(复用 `RAGService._cached` 那条
路径)。不这么报的话,这个答案在埋点里与「模型刚刚生成」完全一样,于是
「缓存给出错答案」这件事永远查不到源头。
